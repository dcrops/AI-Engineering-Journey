# Purpose

This document is the single source of truth for producing every video associated with the AI Engineering Journey portfolio.

It defines:

- the purpose of the videos
- the target audience
- the production philosophy
- visual style
- narration style
- editing workflow
- project order
- quality standards

Every future video should follow this guide to ensure consistency across the entire portfolio.

---

# Project Vision

The portfolio already demonstrates technical capability through interactive engineering walkthroughs.

The videos exist to make those projects easier to understand, more memorable and more engaging.

They are **not tutorials**.

They are **engineering case studies**.

The objective is to communicate:

- engineering thinking
- architectural decisions
- software engineering maturity
- AI engineering capability

rather than simply demonstrating application features.

---

# Guiding Principles

Every production decision should follow these principles.

1. Show rather than tell.

2. Demonstrate engineering decisions rather than application features.

3. Explain *why* something was built before explaining *what* it does.

4. Motion should communicate information, not decoration.

5. Real software is more persuasive than conceptual diagrams.

6. Keep explanations concise.

7. Reuse visual language across every video.

8. Optimise for busy recruiters.

9. Maintain premium production quality.

10. Finish videos rather than endlessly polishing them.

Every project should broadly follow the same structure.

---

## 2. Problem

Explain the engineering challenge.

---

## 3. Engineering Solution

Explain the architectural approach.

---

## 4. Architecture

Show:

- pipeline
- components

Use animated overlays where appropriate.

---

## 5. Demonstration

Show the real application.

Alternate between:

- application

Reinforce the project's strongest achievements.

---

## 7. Closing

Finish with consistent branding.

# Narration Style

Narration will be AI-generated using OpenAI Text-to-Speech.

The same narrator should be used across the entire portfolio.

Narration should sound like:

- an experienced software engineer
- presenting to another engineer
- during an interview or conference presentation

Avoid:

- marketing language
- corporate buzzwords
- dramatic movie trailer narration

Prefer:

- natural conversation
- shorter sentences
- thoughtful pauses
- clear engineering explanations

Scripts should be written for spoken language rather than documentation.

Narration Principles

Narration should explain:

• engineering decisions
• architectural reasoning
• implementation choices
• operational value
• trade-offs

Narration should avoid explaining:

• button clicks
• cursor movement
• scrolling
• obvious UI elements

The visuals explain what the viewer is seeing.

The narration explains why it matters.

# Motion Design

Movement should only be used when it improves understanding.

Preferred:

• subtle push-ins
• gentle pans
• freeze frames
• crops
• highlight framing
- animated highlights
- cursor spotlight
- architecture overlays
- subtle fades
- timeline reveals

Avoid:

- spinning transitions
- unnecessary effects
- distracting animation


Static shots are perfectly acceptable when the composition is already strong.

Freeze Frames

Freeze frames are encouraged when they:

• allow narration to complete naturally
• give viewers time to absorb complex visuals
• avoid unnecessary re-recording

Freeze frames are preferred over artificially slowing screen recordings.

# Portfolio Production Toolkit

Throughout production we will build a reusable set of editing techniques.

New techniques should only become part of the portfolio standard if they satisfy all of the following:

- They improve communication.
- They are reusable across multiple projects.
- They are practical to reproduce.
- They contribute to a premium production style.

The objective is to develop a consistent editing language across the entire portfolio rather than introducing different effects for every video.

Examples include:

- subtle push-in zooms
- slow camera pans
- highlight boxes
- animated callouts
- cursor spotlighting
- architecture overlays
- animated arrows
- reusable branded opening
- reusable closing sequence

Avoid effects that exist purely for decoration.

Every visual effect should help the viewer understand the engineering.

# Editing Guidelines

Maintain visual momentum.

Something should normally change every 3–6 seconds.

This may include:

• a cut
• camera movement
• a freeze frame
• a crop
• a transition
• a new visual

Do not introduce movement purely to satisfy this guideline.

Movement should always communicate information.

# Production Workflow

Every project should follow the same engineering-first workflow.

1. Define the engineering story.

Identify the business problem, architectural decisions, implementation approach and operational value before recording.

↓

2. Record one continuous walkthrough.

Record the entire application or repository in a single OBS session.

Avoid recording many small clips.

↓

3. Build the visual story first.

Edit the visuals into a coherent engineering narrative.

Do not write narration yet.

↓

4. Divide the edit into timelines.

Typical structure:

• Timeline 1 — Problem & Architecture
• Timeline 2 — Engineering Implementation
• Timeline 3 — Execution
• Timeline 4 — Outcomes

↓

5. Write narration for each timeline.

Narration should be written after the visuals are largely complete.

The visuals determine the pacing.

↓

6. Lock each timeline.

Once narration and visuals work together, avoid revisiting that timeline unless absolutely necessary.

↓

7. Assemble the master timeline.

Join all timelines together.

Review pacing and transitions.

↓

8. Add music.

Only after the edit is effectively complete.

↓

9. Export.

↓

10. Portfolio integration.

Do not skip stages.

# Production Lessons Learned

The first trailer established several standards.

## Screen Recording

- Record at 4K.
- Use OBS Studio.
- Record the complete webpage once.
- Reframe in DaVinci using zoom and position.
- Crop where appropriate to isolate projects.

## Motion

Subtle movement is preferred.

Use:

- slow push-ins
- gentle pans
- subtle fades

Avoid unnecessary animation.

## Composition

Treat every clip like a photograph.

Each shot should have a single visual subject.

The viewer should immediately understand what they are looking at.

## Editing Philosophy

Do not optimise for readability.

Optimise for curiosity.

The website provides the detail.

The videos provide the emotional engagement.

Payroll Diagnostics Lessons

• One long OBS recording is more efficient than many short recordings.
• Build the visual story before writing narration.
• Timeline-based editing simplifies production.
• Freeze frames improve narration timing.
• Narration should explain engineering decisions rather than UI interactions.
• Lock completed timelines before assembling the final edit.
• Premium production comes from restraint rather than excessive effects.
